# Default agent instructions

These are common instructions for agents across all scenarios.

## General Guidelines

- Write a plain dash "-" wherever an em dash would go.
- When writing commit messages, NEVER auto-add your agent name as co-author.
- Change CHANGELOG.md files and any file marked as auto-generated by rerunning the generator that owns them.
- When writing or substantially editing long Markdown files, put each full sentence on its own line.
  Preserve normal Markdown structure, but avoid wrapping multiple sentences onto one physical line.
- When making technical decisions, prefer quality, simplicity, robustness, scalability, and long term maintainability, and let development cost weigh little.
- Prefer an established tool over a hand-rolled one, even when the hand-rolled one looks small.
  Before rejecting a candidate tool, check whether it is genuinely a standard or merely popular, and say which.
- Test a tool before arguing against it: install it in a scratch directory, drive it against a fake target, and read its own documentation first.
  Assertions about caching, defaults, flags, and file modes are cheap to test and frequently wrong.
  When a test contradicts an argument that has already been made, retract the argument explicitly rather than quietly moving on.
- A repo's scope is bounded by its name.
  Put adjacent concerns in a separate repo and propose it, even when bundling them is convenient.
  A repo named `dotfiles` holds dotfiles, not container images or editor GUI state.
- Give concepts real names, because nothing tracks an invented numbered label.
- When multiple open questions accumulate (e.g. after a code review or multi-part investigation), ask them one at a time, not bundled together.
  Wait for an answer before asking the next.

## Bug fixes

- When doing bug fixes, always start with reproducing the bug in an E2E setting as closely aligned with how an end user would experience it as possible.
  This makes sure you find the real problem so your fix will actually solve it.

## Testing and quality

- When end-to-end testing a product, be picky about the UI you see and be obsessed with pixel perfection.
- Fix what clearly looks off, even when it is unrelated to the current work and not caused by it: a UI detail, a lint error, a test failure, a flaky test.

## Design sessions

- When asked to propose, show, or compare options, present them as prose mock-ups, leave repo files untouched until a decision is made, and wait for that decision.
  Present a design of symbols, wording, or layout by simulating the output; run a tool when the question is that tool's behaviour.
- In a design or grilling session, the deliverable is written decisions - issues, ADRs, glossary terms.
  When a change surfaces mid-session, propose it with a recommendation and ask whether to implement it or file it; default to filing.
  This is about code: applying a settings change that gates other work is welcome when asked for directly.

## Git and CI

- Git hooks must reject non-conforming commits, never silently fix them.
  Formatters and linters run in `--check` mode in a pre-commit hook, not `--write` or `--fix`.
  Auto-fixing means the committed content differs from what was reviewed and staged.
  The developer runs the fix command themselves and commits again.
- When writing github workflows, use the latest actions.
  Use hash references.

## Memory

Persist durable facts as Markdown in the two places below.
Machine-local agent state, such as anything under `~/.claude/projects/`, is lost on machine re-install, so it is not a place for memory.

- Facts that apply everywhere go in `~/AGENTS.md`, which is symlinked to `~/.claude/CLAUDE.md`.
- Facts that apply to one repo go in that repo's `AGENTS.md`, committed alongside the code.
